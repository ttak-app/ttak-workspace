# 작업 명세: CI 세팅

## 연결 정보

- 브랜치: chore/ci-setting/#3

## 목적

Swift macOS 앱과 React 랜딩 페이지를 서로 독립된 검증 대상으로 관리한다.
PR의 변경 파일과 실제 실행 의존성을 확인해 필요한 검사만 실행하고,
관련 없는 앱의 빌드, 의존성 설치와 테스트에 리소스를 사용하지 않는다.
이후 랜딩 페이지 CD도 변경된 대상만 배포하도록 연결할 수 있게 설계한다.

## 작업 범위

### 포함

- `.github/workflows/ci.yml`에서 변경 감지, 대상별 조건부 검사, 최종 결과 취합을 구현한다.
- main, develop 대상 PR의 전체 변경을 기준으로 앱, 웹, 하네스의 검사 대상을 결정.
- 앱과 웹이 각각 변경된 경우 해당 검사만 실행하고, 둘 다 변경되면 병렬 실행.
- 하네스의 구조 검사와 도구 회귀 테스트를 구분해 문서 변경에 불필요한 회귀 테스트 생략.
- 공통 파일의 실제 사용 범위에 따른 영향 분류와 삭제, 이동, 감지 실패 처리.
- 단일 필수 검사 `CI Result`의 성공, 실패와 의도된 생략 판정 기준.
- 변경별 검증 시나리오, 후속 원격 실행 확인과 필수 검사 연결 계획.
- `.gitignore` 단독 변경은 실제로 하네스 구조 검사만 선택하고, `.tmp/` 제외 규칙 누락의 실패가 최종 결과에 전파되도록 연결한다.
- 참고 PR과 동일한 기본 PR 이벤트를 사용하고 `edited`, `ready_for_review` 트리거와 편집 전용 조건을 제거한다.
- 작업 이름은 고정하고 concurrency는 PR 번호를 기준으로 단순화한다. 제목과 본문 편집은 실행 기록 자체를 만들지 않는다.

### 제외

- 현재 요청에 포함되지 않은 커밋, push, PR 수정, merge 및 원격 필수 검사 연결. 구현 후 게시와 실제 실행 확인 단계에서 진행한다.
- 새 PR과 이슈 생성, 원격 ruleset 변경.
- 랜딩 페이지 호스팅 선정과 CD 구현, 앱 서명, 공증과 배포.
- Swift 테스트 타깃 신설, 새 코딩 컨벤션 도구, 자동 라벨링과 추가 브랜치 정책.
- 앱 기능, 하네스 엔진, 앱 의존성 및 잠금 파일의 무관한 변경.
- 변경 감지를 위해 Turborepo나 Nx 등 별도 모노레포 프레임워크 도입.

## 설계 결정

### 처리 흐름과 책임

1. `Changes`: 가벼운 Ubuntu 작업에서 PR 전체 변경을 수집하고 검사 대상 플래그를 출력한다.
2. `macOS Build`, `Web`, `Harness`: 각 플래그에 따라 필요한 작업만 실행한다. 필요한 작업끼리는 병렬 실행한다.
3. `CI Result`: 감지 결과와 각 작업의 실제 종료 상태를 대조해 최종 병합 판정 결과를 만든다.

CI 정의는 기존 `ci.yml` 하나 안에 둔다. 앱과 웹 사이에 코드 의존성이 있다고 가정하지 않는다.
일반 PR에서는 변경 감지와 결과 취합만 항상 실행하며, 생략 대상 작업에는 runner를 할당하지 않는다.
특히 웹만 변경한 PR에서 macOS runner를 시작하거나 Xcode를 실행하지 않는다.
문서만 변경한 PR에서 웹 의존성 설치와 앱 빌드를 수행하지 않는다.

### 변경 감지

- PR의 마지막 커밋 하나가 아니라 대상 브랜치와 비교한 PR 전체 변경을 판별한다.
- `pull_request`에 `types`를 지정하지 않아 PR 생성, 추가 커밋과 다시 열기에서만 실행한다.
- 제목과 본문 수정, Draft 해제만으로는 워크플로를 호출하지 않는다. 이 변경에 따른 별도 스킵 기록도 만들지 않는다.
- PR 대상 브랜치만 변경해도 자동 재실행하지 않는다. 새 대상 검증이 필요하면 PR을 닫았다 다시 열거나 새 커밋을 push해 새 이벤트에서 감지한다. 과거 실행을 단순 재실행해 새 대상 검증을 대신하지 않는다.
- concurrency는 PR 번호로 묶고 작업 이름은 Changes, Harness, Web, macOS Build, CI Result로 고정한다.
- 파일 추가, 수정, 삭제를 포함한다. 이동과 이름 변경은 이전 경로와 새 경로의 영향을 함께 확인한다.
- 이번 구현은 기존 Node 기본 모듈과 Git을 사용한다. `Changes`에서 PR merge commit을 `fetch-depth: 0`으로 checkout해 대상과 작업 브랜치의 이력을 확보하고 이벤트의 base SHA와 head SHA의 merge-base부터 head까지 비교한다. REST 파일 목록의 개수 제한이나 새 Action 의존성을 추가하지 않는다.
- Git 명령은 인자 배열로 실행하며 파일 목록은 NUL 구분으로 읽는다. rename 감지를 끄고 삭제와 추가 경로를 모두 얻어 앱 사이 이동의 양쪽 영향을 분류한다.
- 비교에 필요한 commit이나 merge-base가 없거나 Git 명령이 실패하면 감지 실패로 처리한다. 빈 출력이나 실패를 변경 없음으로 간주하지 않는다.
- 모든 작업은 `contents: read`만 사용한다. 토큰이나 사용자 입력을 셸 명령 문자열에 삽입하지 않는다.
- 경로 분류는 검토 가능한 한 곳에 두고, 폴더명이 비슷하거나 루트 파일이라는 이유로 전체 검사를 선택하지 않는다.
- 파일 목록을 얻지 못하거나 불완전하게 수집한 경우에는 '변경 없음'으로 처리하지 않는다. 변경 감지 실패와 최종 결과 실패로 드러낸다.

여러 범위가 변경되면 필요한 검사의 합집합을 실행한다.

- 루트 잠금 파일은 현재 웹 의존성만 관리하므로 Swift 빌드를 선택하지 않는다.
- 루트 `.gitignore`는 구조 검사가 `.tmp/` 제외 규칙을 확인하는 실제 입력이다. 단독 변경에도 구조 검사를 선택하며 앱 빌드, 웹 검사와 하네스 도구 테스트는 선택하지 않는다. `.tmp/` 제외 규칙이 누락되면 기존 구조 검사가 실패해야 한다.
- `.editorconfig`, 개발 및 CI 문서와 GitHub 템플릿은 구조 검사의 필수 입력 또는 연결 대상이므로 구조 검사에 포함한다. 상태 JSON 템플릿은 기존 회귀 테스트도 직접 읽으므로 구조와 도구 테스트를 모두 선택한다.
- 앱 루트 README와 현재 테스트 안내 README는 설명 문서로 생략한다. source, public 및 Resources 내부 Markdown은 앱 리소스일 수 있으므로 앱 검사에 포함한다.
- 루트 `package.json`은 현재 모든 검증 진입 명령과 npm 실행 환경을 정의하고, `.nvmrc`는 모든 작업에서 사용한다. 이 두 파일은 현재 구조에서 공통 검사 대상으로 분류한다.
- CI와 감지 정의 변경은 작업 선택 자체를 바꾸므로 전체 경로의 연결을 검증한다.
- 새 공용 패키지나 실행 설정을 도입하면 실제 소비 대상을 확인해 영향표와 검증 사례를 함께 갱신한다. 현재 없는 앱 간 의존성을 미리 추가하지 않는다.

### 구현 파일과 입출력

- CI 진입과 job 연결은 `.github/workflows/ci.yml`에서 관리하고 분류 및 판정 로직은 `tools/ci`의 Node ESM 도구에 둔다. 새 npm 의존성이나 모노레포 프레임워크는 도입하지 않는다.
- 순수 함수로 경로 분류와 최종 판정을 검증하고, CLI는 Git, Actions의 출력 파일과 환경 변수 입출력을 담당한다. 테스트는 `tools/ci/*.test.mjs`에 둔다.
- `Changes`는 감지 성공을 나타내는 버전과 완료 표식, `macos`, `web`, `harness_structure`, `harness_tests` 네 플래그를 출력한다. 플래그는 정확한 문자열 `true` 또는 `false`로 전달한다.
- 일반 설명 파일처럼 의도적으로 검사를 생략하는 경로를 명시한다. 알려지지 않은 코드나 실행 설정 경로는 자동 생략하지 않고 분류 필요 오류로 드러낸다. 실제 분류표의 보조 경로는 소비 도구와 검증 사례를 확인해 구현 문서에 기록한다.
- `Harness`는 두 하위 단계의 실제 결과를 각각 출력한다. 도구 테스트가 선택되면 기존 `workflow:test`와 새 CI 도구 테스트를 실행하며, 구조 검사만 선택되면 도구 테스트를 생략한다.
- `CI Result`는 `toJSON(needs)`를 환경 변수로 전달받아 감지 표식, 엄격한 플래그, job 결과와 Harness 내부 결과를 함께 검증한다. 환경 변수 JSON을 실행 코드로 평가하지 않는다.
- 각 플래그와 실행 또는 생략 이유 및 최종 판정은 Actions step summary에 기록한다. 파일명에 포함된 문자로 명령을 실행하거나 출력 파일 형식을 깨뜨리지 않도록 출력한다.

### 대상별 실행

- `Web`: 기존 Ubuntu 환경에서 `npm ci` 후 `lint:web`, `check-types:web`, `build:web`를 실행한다. 선택되지 않으면 설치부터 생략한다.
- `macOS Build`: 기존 macOS 26, Xcode 26.6 환경에서 `npm run macos:build`로 서명 없는 Debug 빌드를 수행한다. 선택되지 않으면 작업 전체를 생략한다.
- `Harness`: 구조 검사와 도구 테스트의 선택 결과를 별도 플래그로 관리한다. 구조만 바뀌면 `workflow:harness-check`만 실행하고 도구 회귀 테스트는 생략한다. 도구가 바뀌면 필요한 구조 검사와 기존 `workflow:test`를 실행한다.
- 하네스와 macOS 실행 도구는 Node 기본 모듈을 사용하므로 웹 의존성을 설치하지 않는다.
- Node 24, npm 11.3.0, 공식 Actions SHA 고정, 웹 npm 다운로드 캐시, PR별 이전 실행 취소와 시간 제한은 기존 구성을 유지한다.
- 현재 Swift 테스트 타깃이 없으므로 `macos:test`는 추가하지 않는다. 하네스 도구 테스트 통과를 Swift 앱 테스트 통과로 표현하지 않는다.

### 최종 결과와 병합 조건

워크플로 전체를 경로 필터로 생략하지 않고, 내부 검사 작업에 조건을 적용한다.
`CI Result`는 감지와 검사 작업들에 의존하며 선행 작업의 실패나 생략에도 실행되도록 구성한다.
`CI Result`는 `always()`를 사용한다. 감지 실패로 필요한 job이 실행되지 않아도 최종 판정을 수행한다. 제목과 본문 편집은 워크플로를 호출하지 않으므로 별도 결과도 만들지 않는다.
필수 상태 검사는 구현 게시와 실제 실행 확인 이후 `CI Result` 하나로 연결한다. 이번에는 원격 설정을 변경하지 않는다.

| 관측 결과 | `CI Result` 판정 |
| --- | --- |
| 변경 감지 성공, 선택한 모든 검사가 성공 | 성공 |
| 변경 감지 성공, 선택하지 않은 검사가 의도대로 생략 | 성공 |
| 일반 문서 변경으로 무거운 검사가 모두 불필요 | 감지와 대상 분류를 확인한 후 성공 |
| 선택한 검사 실패 또는 취소 | 실패 |
| 선택한 검사가 예상과 달리 생략되거나 필수 출력 누락 | 실패 |
| 변경 감지 실패, 취소 또는 결과 불명확 | 실패 |
| 감지 완료 표식 누락, 잘못된 플래그 또는 선택한 Harness 내부 단계 결과 누락 | 실패 |

항상 실행되는 결과 취합 작업은 설치나 빌드를 반복하지 않고 상태만 확인한다.
`continue-on-error`나 모든 skipped 상태의 무조건 성공 처리로 실제 실패를 숨기지 않는다.
PR 요약에 변경으로 선택한 검사와 생략 이유를 남겨 실행 범위를 확인할 수 있게 한다.

### 후속 CD 연결

현재 작업에서는 CD를 구현하지 않는다.
후속 웹 CD는 main에 실제 반영된 변경을 기준으로 배포 대상을 판별하고,
웹에 영향이 있는 경우에만 필요한 검증 성공을 확인한 뒤 배포한다.
PR 실행의 임시 플래그를 main의 배포 실행에서 그대로 사용할 수 있다고 가정하지 않는다.
Swift만 변경됐다면 랜딩 페이지를 배포하지 않는다.

### 구현과 원격 확인 단계

- revision 4의 변경 감지와 최종 판정 구현은 유지하고 revision 5에서 참고 PR과 동일한 기본 이벤트 및 고정 작업 이름으로 단순화한다.
- 기존 승인 0명, 직접 push 차단과 Merge commit 정책 및 `.gitignore` 분류를 유지한다. 대상 변경 자동 처리를 요구했던 CI-R2-002는 사용자의 이번 트리거 변경 지시로 대체하며 이전 리뷰 기록은 보존한다.
- 운영 문서와 Git 기준을 현재 구현 및 게시 전 상태에 맞춰 갱신한다. 기존 PR 설명과 원격 규칙은 이번에 변경하지 않는다.
- 로컬 분류 및 판정 테스트와 workflow 정적 검증을 수행한다. 실제 Git 이력으로 여러 커밋, 삭제 및 이동이 분류되는지도 확인한다.
- 로컬 구현을 확인한 AC와 미실행 GitHub 시나리오를 구분해 기록한다. AC-6은 게시 후 실제 선택 실행과 필수 검사 연결까지 대기로 남긴다.
- 기존 기본 CI의 원격 성공은 보존하되 새 조건과 최종 판정의 성공 증적으로 재사용하지 않는다. 전체 Xcode 라이선스 상태와 무관하게 미실행 앱 빌드를 통과로 표시하지 않는다.

기존 완료 조건의 ID를 유지하고 이번 구현의 구체적인 경계 검증을 AC-10으로 추가한다.

## 완료 조건

- AC-1: main, develop 대상 PR의 전체 변경을 감지하고 Swift만 변경하면 macOS 빌드만, 웹만 변경하면 웹 검사만 선택한다. 양쪽 변경은 병렬 검사하며 PR 생성, 추가 커밋과 다시 열기에서 현재 대상 기준으로 선택 결과를 갱신한다.
- AC-2: 기존 npm 명령을 재사용하고, 선택되지 않은 앱의 runner 할당, 의존성 설치, 린트, 타입 검사와 빌드를 생략한다. 하네스 구조 검사와 도구 테스트도 별도로 선택한다.
- AC-3: 선택된 macOS 작업은 macOS 26과 명시한 Xcode 26 환경에서 기존 unsigned 빌드를 실행한다. 웹과 일반 문서만 변경한 PR에서는 macOS 작업을 실행하지 않는다.
- AC-4: 버전 선택, 필요한 의존성 설치와 캐시, 작업별 최소 권한, 시간 제한과 PR 이전 실행 취소를 유지하고 워크플로 정적 검증을 통과한다.
- AC-5: 운영 문서에 변경 영향표, 선택과 생략 이유, `CI Result` 판정, Swift 테스트 부재, 후속 CD와 원격 확인 상태가 정확히 설명된다.
- AC-6: 게시 후 실제 GitHub의 선택 실행과 생략, 최종 판정을 확인하고 main, develop의 필수 검사를 `CI Result`로 연결한다. 원격 확인 전까지 대기 상태로 남긴다.
- AC-7: 루트 잠금 파일, `.gitignore`, 하네스 문서, 실행 도구, 공통 환경과 CI 정의 변경을 영향표에 따라 분류하며 파일 삭제와 이동도 누락하지 않는다. `.gitignore` 단독 변경은 하네스 구조 검사만 선택하고 `.tmp/` 제외 규칙이 누락되면 실패한다.
- AC-8: 변경 감지나 필요한 검사가 실패, 취소되거나 예상과 달리 생략되면 `CI Result`가 성공하지 않는다. 관련 없는 검사의 의도된 생략은 병합을 막지 않는다.
- AC-9: `.gitignore` 분류와 실패 전파를 유지한다. 참고 PR처럼 `pull_request` 기본 이벤트만 사용하고 `edited`와 `ready_for_review`는 추가하지 않는다. 제목과 본문 수정은 워크플로 호출이나 스킵 기록을 만들지 않는다. 작업 이름은 고정하고 concurrency는 PR별로 묶는다. 대상 브랜치만 바꾸면 자동 검증하지 않는 한계를 문서에 명시한다.

- AC-10: PR 이력 기반 분류와 CI Result의 정상 및 실패 경계를 자동 검증한다. 감지 실패, 잘못된 플래그, 필수 결과 누락, 선택한 검사 실패/취소/생략과 Harness 내부 단계 누락은 실패하며, 관련 없는 검사 생략과 일반 문서 변경은 성공한다. 기본 PR 트리거와 고정 작업 이름 및 선택 조건 연결을 검증한다.

앱과 웹의 기존 검사 결과만으로 새 변경 감지와 최종 판정이 검증됐다고 표현하지 않는다. 로컬 분류와 실패 판정 검증, 실제 GitHub 실행 결과를 구분해 기록한다.

## 미결정 사항

- 제품 정책과 실행 범위의 미결정 사항은 없다.
- 감지 수단은 Node와 Git으로 확정했다. 분류와 출력 표현은 위 영향표와 실패 처리 기준에 맞춰 구현 및 검증한다.
- 원격 실행과 필수 검사 연결은 게시 후 단계이며 현재는 수행하지 않는다.
