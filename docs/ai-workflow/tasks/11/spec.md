# 작업 명세: CI Result 필수 병합 조건 연결 누락 수정

## 연결 정보

- 이슈: #11 / https://github.com/ttak-app/ttak-workspace/issues/11
- 브랜치: feat/ci-required-check/#11
- specRevision: 1

## 목적

기존 CI의 최종 판정인 `CI Result`를 main과 develop의 필수 상태 검사에 연결한다.
검사가 실패하거나 완료되지 않은 상태에서는 병합을 차단하고, 성공하면 기존 PR 병합 절차를 유지한다.

## 작업 범위

### 포함

- 기존 `ttak-main`, `ttak-develop` ruleset의 현재 설정과 실제 GitHub Actions check run 확인.
- 각 ruleset에 `CI Result` 하나를 필수 상태 검사로 추가하고 적용 상태 확인.
- 변경 전후 설정을 로컬 `.tmp/ai-workflow/tasks/11/`에 보관하고 기존 보호 정책 보존 확인.
- 현재 상태와 맞지 않는 CI 운영 설명을 관련 문서에서 최소한으로 갱신.

### 제외

- CI 워크플로, 변경 감지, 앱 검사 및 의존성 변경.
- 새 ruleset, 새 이슈, 추가 필수 검사나 리뷰 승인 정책 도입.
- 검증용 PR 생성, 임의 check run 작성, 실제 병합이나 기존 PR 상태 변경.
- 커밋, push, PR 게시, merge 및 이슈 닫기.
- 과거 #3 명세의 이력 재작성, 앱 배포와 CD 구축.

## 설계 결정

- 파일 구조와 로직의 책임: 원격 GitHub ruleset이 병합을 제한한다. 기존 `ci.yml`과 `tools/ci/result.mjs`는 최종 판정을 제공하므로 수정하지 않는다. 이 명세와 관련 운영 문서에는 실제 확인한 상태만 기록한다.
- 상태 및 데이터 흐름: 기존 경로별 CI 실행 → 고정 이름 `CI Result` 생성 → 대상 브랜치 ruleset이 결과를 필수 조건으로 판정.
- 선택한 방식과 이유: 기존 활성 ruleset의 대상 조건, 우회 설정과 기존 규칙을 유지하고 `required_status_checks`에 필요한 항목만 추가한다. 실제 Actions check run의 이름과 GitHub App 식별자를 확인하고 가능한 경우 해당 제공자로 한정한다. 최신 대상 브랜치 반영 강제 등 별도 정책은 도입하지 않는다.
- 변경 절차: 변경 직전 원격 설정을 다시 읽고 백업한다. main과 develop은 하나씩 변경하며 각 변경 직후 재조회한다. 이미 동일한 설정이 있으면 중복 생성하지 않는다.
- 예외 처리: 권한 부족이나 API 오류는 성공으로 처리하지 않는다. 일부만 반영되면 적용된 대상과 남은 대상을 명확히 보고한다. 기존 정책이 바뀌면 원인을 확인하고 이번 작업이 변경한 부분만 복구한다.
- 검증 한계: ruleset 저장 성공, 실제 적용 규칙과 check run 결과를 구분한다. 실패 또는 대기 중인 PR을 실제로 관찰하지 않았다면 병합 차단 실증은 미검증으로 남긴다. 성공한 CI만으로 실패 차단 실증을 대체하지 않는다. 실제 merge는 검증에 사용하지 않는다.

## 완료 조건

- AC-1: main과 develop에 적용되는 활성 ruleset에서 실제 Actions 제공자의 `CI Result`가 필수 검사로 지정되어 있다.
- AC-2: 대상 브랜치, 활성 상태, 우회 설정, PR 필수, 승인 0명, Merge commit, 삭제 및 force push 차단 등 기존 설정이 유지된다. 불필요한 필수 검사나 최신 브랜치 반영 강제를 추가하지 않는다.
- AC-3: 각 브랜치의 적용 규칙과 실제 GitHub check run을 확인한다. 실패 및 대기 시 병합 차단과 성공 시 해당 조건 충족 여부는 실제 관찰과 설정 확인을 구분해서 보고한다.
- AC-4: 관련 운영 문서의 필수 검사 연결 상태가 실제 설정과 일치하고, 하네스 구조 검사와 diff 검토를 통과한다.

## 검증 방법

| 완료 조건 | 확인 방법 | 기대 결과 |
|---|---|---|
| AC-1 | 실제 check runs, ruleset과 각 브랜치의 적용 규칙 GET | `CI Result` 이름과 제공자가 일치하며 양쪽에서 필수 검사로 적용 |
| AC-2 | 변경 전후 JSON 비교 | 필수 상태 검사 추가 외 기존 설정에 의미 있는 변경 없음 |
| AC-3 | 읽기 전용 PR 및 check run 조회, 적용 규칙 대조 | 실제 관찰한 성공/실패/대기와 설정 기반 판단 및 미검증 구분 |
| AC-4 | `npm run workflow:harness-check`, `git diff --check`, 문서 검토 | 구조와 링크 정상, 현재 상태 설명 일치 |

## 미결정 사항

- 추가 정책 결정은 없다. 실제 실패 및 대기 PR이 없으면 해당 동작 실증은 후속 PR에서 확인할 항목으로 남긴다.
