# 해석할 수 없는 시작 시각 처리 설계안

## 목적과 상태

브랜치 리뷰의 `BRANCH-2026-01`을 해결하기 위한 제안이다. 이 문서는 구현 완료나 새로운 제품 UX의 확정을 뜻하지 않는다. 현재 작업 범위인 Gemini 연동 및 핵심 로직 검증을 유지하며 사용자 확인 UI와 실제 미리 알림 저장의 제품화는 후속으로 둔다.

## 현재 문제

`내일 밤 1시에 서버 점검`에서 Gemini가 원문을 정확하게 반환하더라도 `groundSources`가 `ScheduleTimeParser.clock`으로 변환되지 않는 시각을 버린다. `validate`도 변환된 시각만 후보로 세기 때문에 `시각 없음`과 `시각은 있으나 변환 불가`를 구분하지 못한다. `makeDraft`는 시각 원문이 전달됐을 때 확인 필요 메모를 남길 수 있지만 해당 경로에서는 `nil`을 받는다. `ScheduleDraft.validationMessage`는 빈 시각을 허용하므로 확인 없이 시각이 없는 초안이 저장될 수 있다.

`밤 1시`와 `저녁 7시`의 24시간 표현을 새로 정하는 문제가 아니다. 합의하지 않은 시각 해석은 하지 않고, 변환하지 못한 사실을 사용자에게 전달하는 문제다.

## 권장안: 분석 보류

원문에 명시된 시작 시각이 있으나 기존 규칙으로 확정할 수 없으면 전체 분석 결과를 반환하지 않고, 해당 원문 표현을 포함한 확인 안내를 제공한다. 사용자는 입력을 명확하게 고쳐 다시 분석한다. 예를 들어 `내일 밤 1시에 서버 점검`은 `밤 1시`를 보존하고, `시작 시각 '밤 1시'를 확인할 수 없어요. 오전 또는 오후와 숫자 시각을 명확하게 입력하세요.`와 같이 안내한다.

- UI에 새로운 시간 확인 컴포넌트나 저장 상태를 추가하지 않는다.
- 기존 가드가 여러 후보 중 하나라도 문제를 발견하면 전체 결과를 보류하는 경계를 유지한다. 여러 일정 중 한 건이 확인 필요해도 나머지만 부분 반환하지 않는다.
- 처음부터 시각이 없는 일정과 숫자가 없는 `저녁에 회의`는 기존처럼 빈 시각을 허용한다. 이는 사용자의 시각 확인을 거쳤다는 의미는 아니다.
- 변환 불가 사실은 Swift에서 판정한 결정적 결과이므로 같은 원문에 대한 Gemini 재호출로 고치려 하지 않는다. 기존 가드의 모델 재분석 피드백과 별도의 확인 필요 결과 또는 타입화된 오류로 전달하고, 현재 최대 한 번인 모델 재분석 한도는 변경하지 않는다.
- 오류에 담는 표현은 해당 일정 원문에 실제 존재하는 부분만 사용한다. 일반 앱 로그, Git 또는 공유 증적에는 개인 원문을 저장하지 않는다.

## 처리 설계

1. 모델은 지금처럼 일정별 연속 원문을 반환한다. 날짜와 시각 또는 확인 상태를 모델이 새로 만들어 내도록 요구하지 않는다.
2. Swift가 각 일정 구간의 정규식 일치 항목에서 **원문 문자열과 실제 위치**를 보존한다. 같은 `9시`가 여러 번 나와도 앞의 `9시까지`와 뒤의 `9시에`를 구별한다.
3. 하나의 공통 분류 경로로 각 시각 근거의 역할을 판단한다. 명시적인 종료 시각과 발송 및 작성 시각 같은 메타정보는 시작 후보에서 제외하고, 역할을 안전하게 판별할 수 없는 경우에는 확정하지 않고 보류한다. 숫자가 없는 시간대 표현은 기존 동작을 유지한다.
4. 해당 일정의 시작 후보가 하나이고 기존 파서가 값을 반환하면 현재 날짜 및 시각 처리로 이어간다. 명확한 범위의 시작 시각, `밤 12시`의 다음 날 00:00과 정상적인 오전 및 오후 규칙은 유지한다.
5. 시작 후보가 하나인데 변환이 불가능하거나 숫자가 유효하지 않으면 그 원문 표현과 함께 확인 필요 오류를 반환한다. 시작 후보가 둘 이상인 경우에는 그중 하나만 유효하더라도 임의로 선택하지 않고 전체 분석을 보류한다.
6. `groundSources`와 기존 행동 복원 경로, `validate`에서 같은 위치 기반 분류 결과를 사용해 한 경로에서는 문제를 감추고 다른 경로에서는 감지하는 불일치를 막는다. 사용자가 입력을 수정한 후의 분석은 새로운 요청이다.

구현 시 기존 `ScheduleGuardResult.issues`는 모델 재분석을 유발하므로, 시각 확인 필요를 단순 문자열로 추가하면 불필요한 유료 API 재호출과 피드백 의존이 생긴다. 원문 근거 위반과 사용자 확인 필요를 구분해 처리해야 한다. 적용 시 기존 모델 재분석 테스트와 실패 UI 전달 경로를 함께 확인한다.

## 대안: 편집 가능한 초안에서 시각 확인

초안에 시각 원문과 `timeNeedsConfirmation` 같은 별도 상태를 두고 저장 검증에서 차단한다. 사용자가 유효한 `HH:mm`을 입력하거나 `시각 없이 저장`을 명시적으로 확정하면 해제한다. 날짜 확인 상태를 시각에 재사용하지 않는다.

이 방식은 여러 일정 중 확인이 필요한 항목을 바로 고칠 수 있지만, 빈 시각 허용 여부, 직접 확인 동작, 여러 항목의 부분 저장과 화면 표시를 함께 결정해야 한다. 현재 브랜치에서 합의한 UI 제외 범위를 넓히므로 권장안의 후속 대안으로 남긴다. 메모에만 경고를 적는 방식은 확인을 강제하지 못하므로 해결책으로 보지 않는다.

## 검증 계획

| 구분 | 입력 또는 조건 | 기대 |
| --- | --- | --- |
| 미지원 시각 | `내일 밤 1시에 서버 점검`, `내일 저녁 7시에 식사`, `아침 9시`, `밤 12시 30분` | 원문 시각을 안내하고 전체 분석 보류. 모델 추가 재호출 없음 |
| 무효 숫자 | `25시`, `9시 60분`, `오후 13시`와 실제 일정 행동 | 시각을 임의로 수정하지 않고 확인 안내 |
| 시각 없음 | `내일 회의`, `내일 저녁에 회의` | 기존 빈 시각 동작 유지 |
| 기존 정상 시각 | `오전 9시`, `오후 1시`, `밤 12시` | 기존 시각과 자정 날짜 이월 유지 |
| 범위 | `오후 1시부터 3시까지`, `밤 1시부터 3시까지`, `오후 1시부터 밤 3시까지` | 각각 13:00, 시작 확인 보류, 13:00. 종료 원문 보존 |
| 종료 및 메타정보 | `18시까지 자료 제출`, `메시지 발송 시각 13:08` | 종료와 메타정보를 시작 시각이나 확인 필요 시작으로 오인하지 않음 |
| 반복 및 충돌 | `9시까지 자료 준비 후 9시에 발표`, `9시 또는 밤 1시에 회의` | 각각 위치별 역할 구분, 시작 후보 충돌 보류 |
| 여러 일정 | `9시 회의하고 밤 1시 점검` | 두 번째 일정에 확인 사유가 귀속되고 전체 분석 보류 |
| 연결 경로 | 합성 모델 응답, 복원 및 검증, 기존 재분석 경계 | 해석 불가 시 추가 모델 호출과 정상 초안 반환이 없는지 확인 |

유형별 Swift 테스트 후 포맷, 앱 빌드 및 테스트를 실행한다. 필요 시 합성 문장으로 실제 Gemini 응답과 가드를 함께 확인하되, 실제 모델 성능과 저장 및 앱 UI 확인으로 일반화하지 않는다. 기존 50건과 새 경계 사례를 구분해 결과를 기록한다. `clockPattern`이 인식하지 못하는 모든 자연어 시간 표현까지 감지한다는 보장은 없다.
