# Git·커밋·PR 컨벤션

저장소 전체의 공통 기준이다. Keeply의 Git Flow와 type 기반 커밋 방식을 가져오고,
Ttak에서 합의한 브랜치·승인·병합·라벨 설정에 맞춘다.

## 브랜치와 흐름

| 브랜치 | 역할 | 경로 |
| --- | --- | --- |
| `main` | 배포 기준 | 배포 시 develop → main PR |
| `develop` | 개발 통합·기본 브랜치 | 작업 브랜치 → develop PR |
| `feat/작업명/#이슈번호` | 새 작업 브랜치의 기본 이름 | 최신 develop에서 분기 |

- 사용자가 기존 또는 다른 이름의 브랜치를 지정하면 이를 따른다. 현재 #4는 `chore/agent-harness-setting/#4`다.
- 원본의 `fix/*` 등 예시만 보고 새로운 브랜치 타입 정책을 자동 추가하지 않는다.
- 이슈 번호를 실제 이슈와 맞추고 `#`가 포함된 이름은 셸에서 작은따옴표로 감싼다.
- `main`·`develop`에 직접 구현·푸시하지 않는다. PR 필수·승인 0명이며 관리자의 우회도 없다.
- `main`·`develop` 삭제와 force push는 차단한다. 자동 브랜치 삭제는 꺼 두고 완료된 작업 브랜치만 필요에 따라 정리한다.
- 병합은 Merge commit. Squash/Rebase merge는 현재 저장소 설정에서 허용하지 않는다.
- 배포 후 필요한 main → develop 동기화도 PR로 진행한다.
- PR 검사는 [CI 운영](../ci.md)을 따른다. 현재 로컬 구성 단계이며 원격 실행 확인과 필수 검사 연결은 남아 있다. 출발 브랜치 이름 자동 검사는 없다.
- 이슈 등록·브랜치 생성·커밋·push·PR·merge는 요청 범위의 권한을 확인한다. 기존 권한을 반복 확인하지 않되 PR 요청만으로 merge하지 않는다.

## 커밋 메시지

기본 형식은 소문자 `type: 설명`이며 설명은 한국어로 작업 목적이 드러나게 작성한다.
본문이 필요하면 빈 줄 뒤에 이유·영향을 적고, 이슈 참조는 `Refs #번호`로 연결할 수 있다.
이슈 번호를 모든 커밋 제목에 강제하거나 이미 존재하는 커밋을 소급 재작성하지 않는다.

| type | 사용 기준 |
| --- | --- |
| `feat` | 새 사용자 기능 |
| `fix` | 잘못된 동작 수정 |
| `docs` | 문서만 변경 |
| `refactor` | 외부 동작을 유지하는 코드 구조 개선 |
| `style` | UI 표현·디자인 변경. 동작 결함 수정은 fix로 구분 |
| `test` | 테스트 추가·수정 |
| `chore` | 하네스·검사·의존성·유지 관리·형식 정리 |
| `deploy` | 배포 설정·배포 관련 작업 |

예:

```text
feat: 분석 결과의 일정 제외 기능 추가
fix: 취소한 분석 결과가 다시 표시되는 문제 수정
docs: Swift 코딩 컨벤션 정리
chore: 하네스 검증 명령 연결
```

커밋 하나는 설명할 수 있는 목적 하나로 구성한다. 단순 파일 개수나 줄 수로 분할하지 않는다.
사용자 변경·미검토 파일·로컬 증적을 함께 스테이징하지 않는다.

## PR

- 새 PR 제목의 기본 형식은 `Type: 설명`: `Feat: 미리 알림 등록 기능 구현`, `Chore: Codex 하네스 세팅`.
  사용자 지정 제목과 이미 있는 PR의 제목은 이유 없이 바꾸지 않는다.
- 이슈 제목은 기존 `[Type] 설명` 형식을 유지하고 PR 제목과 구분한다.
- 기본 형식을 일관되게 쓰며 원본의 다른 형식 `Type(scope): ...`를 에이전트가 번갈아 선택하지 않는다.
- [PR 템플릿](../../.github/pull_request_template.md)으로 문제·최종 변경·검증·관련 이슈를 설명한다.
- 템플릿 변경은 기본 브랜치 develop에 병합되어야 GitHub 작성 화면에 반영된다.
- 이슈 전체를 완료하면 `Closes #번호`, 일부 작업이면 `Refs #번호`를 사용한다.
- 실제 실행한 검증과 실패·미실행·환경 한계를 적는다. 앱 동작 미검증을 하네스 검사 통과로 대체하지 않는다.
- 출발·대상 브랜치와 Merge commit 방식을 확인한다. 1인 프로젝트이므로 다른 사람의 승인 대신 자기 검토·검증 기록을 남긴다.
- push·PR 전에 [로컬 준비 검사](../ai-workflow/README.md)를 확인한다. ready는 게시나 merge 권한이 아니다.

## 라벨

현재 GitHub에 존재하는 이름을 그대로 사용한다. 일반 영문 라벨이나 이모지가 다른 중복을 만들지 않는다.
자동 라벨링은 별도 구성 전까지 설치됐다고 가정하지 않는다.

| 라벨 | 용도 |
| --- | --- |
| `🛠️ FEAT` | 새 기능 |
| `🚨 FIX` | 버그 수정 |
| `✏️ DOCS` | 문서 |
| `🔨 REFACTOR` | 구조 개선 |
| `🎨 STYLE` | UI·디자인 |
| `🍀 CHORE` | 유지 관리·도구·설정 |
| `⭐️ INIT` | 초기 세팅 성격의 작업. 커밋은 chore로 표현할 수 있음 |
| `🚀 DEPLOY` | 배포 |
| `🔥 QA` | 테스트·품질 확인 |
