# Codex 작업 흐름

이슈 → 작업 브랜치 → 설계·명세 → 구현 → 검증 → 브랜치 리뷰 → PR 순서로 진행한다.
Keeply의 작업 기록·증적 흐름을 Ttak의 Codex·macOS 환경에 맞춘다.
읽기 전용 조사·설계·리뷰는 이슈나 작업 브랜치가 없어도 가능하다.
코드 변경·리뷰는 [공통 컨벤션](coding-convention.md)과 대상 언어 문서를,
브랜치·커밋·PR은 [Git 컨벤션](git-convention.md)을 읽고 적용한다.

## 시작과 범위

- 이슈 생성 요청은 이슈만 만든다. 이슈를 임의로 늘리거나 구현까지 진행하지 않는다.
- 구현은 해당 이슈와 사용자 요청 범위의 작업 브랜치에서 한다. 기준은 `origin/develop`이며 다른 기준이면 명시한다.
- 새 브랜치는 `feat/작업명/#이슈번호`를 기본으로 하고, 다른 이름을 사용자가 지정하면 따른다.
  `#`가 있는 브랜치를 셸에 전달할 때는 작은따옴표로 감싼다.
- `main`·`develop`은 PR 필수·승인 0명·Merge commit 방식이다. 기본 브랜치는 `develop`이다.
- 이미 합의된 정보는 다시 인터뷰하지 않는다. 제품 범위나 새 정책을 정하는 결정만 질문한다.
- 설계 시 연결 이슈와 합의한 요구사항을 `docs/ai-workflow/tasks/번호/spec.md`에 기록한다.
  `specRevision`과 고유한 `AC-N`을 사용한다. 합의 변경 시 버전과 관련 검증을 갱신한다.
- 사용자 요청 없는 작업 분해·추가 이슈·코딩 컨벤션·게시·merge를 자동으로 만들지 않는다.

## 변경별 검증

| 변경 | 검증 |
| --- | --- |
| 문서·스킬 | `workflow:harness-check`, 로컬 링크·정책·diff 검토. 앱 빌드는 N/A |
| 하네스 도구 | `workflow:harness-check`, `workflow:test`, 해당 도구 정상·실패·재개 동작 |
| Swift·Xcode 설정 | `macos:build`, 기존 테스트가 있으면 `macos:test`, 변경 기능의 실제 실행 확인 |
| 웹·공유 의존성/빌드 설정 | 기존 `lint:web`, `check-types:web`, `build:web` 및 영향받는 테스트 |
| 권한·AI·미리 알림·UI | 위 검사와 실제 Mac에서 해당 동작·실패·재시도·중복 생성 여부 확인 |

실제 명령은 `npm run 명령` 형식이다. 연결 작업의 검사는
`npm run workflow:check -- --script 명령`으로 로그와 대상을 남긴다.
일반 읽기 전용 검증 요청에서는 직접 명령만 실행하고 기록을 쓰지 않는다.
명령 실행이 사용자 미리 알림을 수정하거나 비용·외부 영향을 만드는 경우에는
그 대상까지 요청 범위에 포함되는지 확인한다.

빌드 통과만으로 권한 요청·한국어 모델 품질·사용자 데이터 저장을 검증했다고 하지 않는다.
테스트 타깃이 없으면 이를 명시한다. `macos:test`는 타깃 부재를 성공 처리하지 않는다.
이슈 #9의 [포맷 자동화](../formatting.md)는 앱별 수정과 검사 명령을 사용한다.
수정한 대상의 포맷을 검사하고, 새로운 린터나 Git 훅을 자동으로 추가하지 않는다.

## 리뷰와 게시

- 커밋·staged·unstaged·새 파일을 모두 포함하고 관련 호출부만 추가로 읽는다.
- 기본 기준: 이슈 완료 조건, 상태와 비동기 수명, 권한·에러·취소·재시도,
  날짜·시간대, 모델 추출값 검증, 등록 시점과 중복 저장, 기존 기능 영향.
- 심각도·파일·줄·사용자 영향·수정 방향을 기록한다. 미해결 High/Medium은 준비 완료가 아니다.
- 스킬 선택이나 리뷰 요청 자체로 서브에이전트를 실행하지 않는다. Codex의 자기 검토도 가능하며 다른 사람의 승인은 필수가 아니다.
- 검사 후 파일·index·HEAD·기준 ref·명세·기록된 환경이 바뀌면 기존 증적의 freshness를 확인한다.
- 게시 전 `workflow:pr-check`로 누락·오래된 로그·미해결 사항을 확인한다.
  ready는 로컬 기술 상태이며 push·PR·merge 권한이 아니다.
- 환경 제약이 있으면 blocked와 원인을 보고한다. 사용자가 미검증 상태의 게시를 명시적으로 요청하면
  예외와 필요한 검증을 PR에 적으며 통과로 표시하지 않는다.
- GitHub 설정이나 CI는 명시적 작업 범위에서만 변경한다. CI 이슈는 #3이다.
